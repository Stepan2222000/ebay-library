# Эталонная спецификация: переписывание библиотеки парсинга eBay

_Версия 1 (v1). Дата: 2026-06-21._

Этот документ **самодостаточен**: вся нужная информация — внутри. Ссылок на другие
спек-файлы нет. Между разделами — внутренние ссылки (по номерам), без дублирования.

---

## 1. Цель и обзор

Мы **полностью переписываем** библиотеку-воркер парсинга eBay в **новую папку**
(пакет `ebay_library`). Переиспользуемые части старого кода **копируем** (см.
раздел 12), остальное пишем заново под новую архитектуру.

Главная идея переписывания: **уйти от тяжёлого браузерного парсинга страниц
товаров**. Раньше каждая страница товара (PDP) грузилась в браузере целиком, что
было медленно и хрупко (зависал ленивый рендер, антибот, таймауты якорей). Мы нашли,
что **данные товара можно тянуть напрямую HTTP-запросом без браузера и без антибота**
(см. раздел 4), а **каталог** (поиск) — параллельными запросами из одной открытой
браузерной страницы (см. раздел 5). Это даёт радикальный рост скорости и надёжности.

**Ключевой принцип парсинга товара: берём данные МАКСИМАЛЬНО из встроенной
JSON-модели страницы.** Страница товара (PDP) — это Marko/Raptor-приложение со
встроенной JSON-моделью (объект `modules` + schema.org-блок `JSONLD`), из которой
фронт и рендерит; из неё берём **почти все** поля готовыми — это **надёжнее DOM** (не
зависит от ленивого рендера, который ломал старый подход). Проверено на 1000 разных
запчастей (раздел 13). **Для каталога (выдача SRP) цельной JSON-модели по карточкам
нет** — там парсим **из DOM** (это штатный путь каталога, не фолбэк; см. раздел 5.3).

Библиотека делится на **два независимых конвейера** («лейна»):

- **Item-лейн** (раздел 4) — массовая дозагрузка данных по товарам. Лёгкий,
  параллельный, **без браузера** (прямые HTTP-запросы). Это основная нагрузка.
- **Catalog-лейн** (раздел 5) — поиск товаров по артикулу (выдача, SRP). Тяжёлый,
  работает через **браузерную страницу**, тоже параллельный.

Лейны **независимы**: каталог пишет свои записи, item — свои, объединяются они уже на
стороне хранилища по `item_id` (см. раздел 2.3). Никакой передачи данных между
лейнами внутри библиотеки нет.

### 1.1. Границы библиотеки (что наше, что нет)

Библиотека — это **парсинг + запись**. Вне библиотеки (забота внешнего
оркестратора): пул воркеров, очередь задач, переотдача задач, **запуск браузера и
управление прокси**, скачивание/хранение фото (S3), решение «рестартить ли упавший
воркер».

Оркестратор общается с библиотекой через **колбэки** (раздел 6): `next_task` (взять
задачу), `task_done` (задача завершена), `get_page` (дать браузерную страницу для
каталога), и клиент хранилища `store`.

### 1.2. Два режима работы (v1 = Mode 1)

- **Mode 1 (реализуем в v1).** Item-лейн тянет товары **с прямого egress сервера,
  без прокси и без куки**, и **цену с доставкой не парсит** — их даёт каталог
  (причина и механика — раздел 4.4).
- **Mode 2 (реализуем позже, раздел 9).** Item-лейн идёт **через US-прокси + куку** и
  становится самодостаточным (цену и доставку отдаёт сам товар).

## 2. Архитектура

### 2.1. Item-лейн (кратко; детали — раздел 4)

Для каждого товара (`item_id`) делаем прямой HTTP-запрос на un-walled CDN-хост eBay,
получаем **полную HTML-страницу товара** и парсим данные **из встроенной JSON-модели**
этой страницы (а не из вёрстки). Описание тянем вторым запросом. Браузер не нужен.
Параллельность — адаптивная (раздел 8).

### 2.2. Catalog-лейн (кратко; детали — раздел 5)

Держим **одну открытую браузерную страницу** на `www.ebay.com` — это живая
антибот-сессия. Запросы страниц выдачи делаем **`fetch`-ом изнутри этой страницы**
(in-page fetch) — параллельно. Парсим карточки из вёрстки (DOM). Параллельность —
адаптивная (раздел 8). При срабатывании антибота («Pardon») — перезагружаем страницу
(страховка, раздел 7.3).

### 2.3. Поток данных и объединение (merge)

Задачи приходят **извне** (оркестратор кладёт их в очередь, библиотека берёт через
`next_task`). Библиотека **не выводит item-задачи из каталога сама** — это внешняя
логика.

Две независимые записи в хранилище:
- **Каталог-воркер** пишет карточки выдачи, и из них же — **цену (USD) и доставку**
  товара (они ZIP/гео-корректны и уже переведены в USD, см. разделы 5.3–5.4).
- **Item-воркер** пишет полные гео-независимые данные товара (специфика, все фото,
  описание, локация, состояние, продавец, дата правки), но **без цены и доставки**
  (в Mode 1; см. раздел 4.4).

**Объединение по `item_id` происходит на стороне хранилища** (server-side логика
`apply_*`, см. раздел 12), а **не в библиотеке**. Библиотека просто отправляет оба
«куска». Общие поля и приоритет при слиянии — забота хранилища.

### 2.4. Топология воркеров

Два **раздельных типа воркера** (раздел 6), потому что лейны разной природы:

- **Item-воркеры** — лёгкие (только HTTP + парсинг JSON, без браузера),
  масштабируются массово. Каждый тянет товары **моментально и параллельно**, поэтому
  их нужно **немного**.
- **Catalog-воркеры** — тяжёлые (держат браузер), их нужно **больше** (браузер —
  узкое место по скорости поиска).

**Масштабирование** — числом воркеров/прокси/браузеров (линейно). В Mode 2 единица
масштаба item-лейна — прокси (один воркер на прокси, раздел 9).

## 3. Endpoints и URL

### 3.1. Хост данных товара (un-walled, без антибота)

- **`https://itm.ebaydesc.com/itm/{item_id}`** — отдаёт **полную HTML-страницу
  товара** (ту же, что `www.ebay.com/itm/{id}`), но **без антибота** (это внутренний
  CDN-хост описаний eBay на Akamai, он вне WAF). Обычный GET, без авторизации.
  Резервный эквивалент: `https://item.ebay.com/itm/{item_id}`.
- **`https://itm.ebaydesc.com/itmdesc/{item_id}`** — **только описание** товара
  (отдельный документ; в основной странице описания нет).
- **Фото**: URL'ы вида `https://i.ebayimg.com/images/g/{imageId}/s-l1600.{jpg|webp}`
  — берём **только URL** из модели, сами картинки **не качаем** (раздел 4.5).

Важно: на этих хостах антибота нет (проверено, раздел 13). Но `www.ebay.com` —
**за антиботом** (прямой HTTP туда даёт 403/503), поэтому каталог идёт через браузер
(раздел 5).

### 3.2. URL выдачи (SRP, через браузер)

`https://www.ebay.com/sch/i.html` с параметрами:
- `_nkw` — поисковый запрос (артикул), URL-энкод;
- `_sacat=0`, `_from=R40`, `rt=nc` — структурные;
- `_ipg=240` — карточек на страницу (и условие конца пагинации — раздел 5.3);
- `_pgn` — номер страницы (1-based);
- `_dmd=1` — **режим list-view** (обязателен: иначе eBay может отдать grid-view, где
  у карточек нет продавца);
- `_stpos=19701` — **ZIP доставки** (задаётся прямо в URL → доставка в карточках
  корректна на каждый запрос);
- опциональные фильтры из задачи: `LH_ItemCondition` (состояние), `_udlo`/`_udhi`
  (мин/макс цена).

### 3.3. Прокси

- **Каталог**: прокси задаётся **при запуске браузера оркестратором** (через
  launch-опцию). Библиотека получает уже готовую страницу (`get_page`) и через неё
  работает; прокси «зашит» в браузер.
- **Item (v1)**: **без прокси** (прямой egress). В Mode 2 — через US-прокси
  (раздел 9).

## 4. Item-лейн (v1)

### 4.1. Транспорт

Запросы делаем библиотекой **`curl_cffi`** (`AsyncSession`), без браузера. **Без
куки и без прокси** в v1.

- **Без `impersonate`** (подделки TLS-отпечатка). Для un-walled `ebaydesc` она не
  нужна, а живьём оказалась **вредной**: с `impersonate="chrome"` eBay отдаёт другую,
  бо́льшую страницу, на которой ломается извлечение встроенной JSON-модели → ParseError
  на части товаров (этап 2). В Mode 2 тоже не понадобится — хост тот же, без WAF.
- **Обязателен заголовок `Accept-Language: en-US`** — иначе eBay отдаёт страницу в
  локали гео запроса (title/specifics не на английском).
- Сессия **долгоживущая, одна на воркер** (`max_clients` = конкуренция `C`, раздел 8);
  per-call сессии не плодим (иначе исчерпание коннектов). Создаётся воркером, в
  транспорт-функции передаётся аргументом.

### 4.2. Порядок запросов на товар

1. Запрос **`itm/{id}`** (основные данные). С **ретраями** на транзиент (раздел 7.1).
2. **Только если основной запрос успешен** — запрос **`itmdesc/{id}`** (описание),
   тоже с ретраями. Без основных данных описание бесполезно, поэтому его не тянем,
   если основной запрос не удался.
3. Парс (4.3), запись в хранилище, `task_done` — **строго после записи**.

### 4.3. Парсинг — из JSON-модели, не из вёрстки

Страница товара содержит **встроенную JSON-модель** (объект `modules`), из которой
сам фронт eBay рендерит. Мы парсим **из неё**, а не из DOM-вёрстки — это надёжнее (не
зависит от ленивого рендера, который ломал старый подход).

**Пример, код извлечения и точная карта путей полей — в `examples/`**
(`examples/item_modules_sample.json` + таблица путей в `examples/README.md`,
раздел 1). Здесь — только суть словами, без дублирования путей.

Данные берём из **двух** embedded-источников в HTML:
1. **объект `modules`** (извлекаем самый крупный `"modules":{...}`, разбираем как
   JSON): заголовок и состояние — из schema.org-блока `JSONLD`; номер товара и дата
   правки — из модуля сводки; локация — из модуля доставки; характеристики
   (specifics, пары ключ→значение) — из модуля «Item specifics»; фото-URL'ы — из
   модуля фото (`mediaList`, нормализуем размер к `s-l1600`, дедуп; **не из
   `JSONLD.image`** — тот обрезан до 5, а `mediaList` несёт полную галерею);
2. **поле `sellerUserName`** — **вне `modules`**, отдельным регексом по полному HTML;
   это **username** продавца (как в каталоге). Слаги `_ssn=`/`/str/` ненадёжны.

(Цена в `modules` тоже есть — в `JSONLD`, но **в Mode 1 не берём**, раздел 4.4.)

Брать значения **напрямую из структуры JSON** (готовые поля), а не регексить текст,
где это возможно. Поиск полей — **по точным путям** (строго), не «поиск по типу
узла»: если eBay сменит структуру — путь не найдётся → `ParseError` → падаем громко
(раздел 7), и мы это сразу замечаем и чиним.

Обязательные/опциональные поля и поведение при отсутствии — раздел 7.4.

### 4.4. Цена и доставка в v1 — НЕ парсятся, ZIP-check ВЫКЛЮЧЕН

Item-лейн в v1 идёт с прямого (не-US) egress, поэтому **цена и доставка** на странице
получаются **чужого гео**: eBay печатает их по гео IP запроса — цена приходит в чужой
валюте (не USD; на прогоне с EU-egress — CZK на всех товарах, раздел 13), доставка —
к чужому ZIP. Поэтому:
- **цену и доставку из товара не парсим и не пишем** — их даёт каталог (кто пишет —
  раздел 2.3; почему они там корректны в USD к ZIP — раздел 5.4);
- **проверку соответствия ZIP не делаем** (она нужна только в Mode 2, раздел 9.3) —
  иначе падали бы на каждом товаре.

Остальные поля (заголовок/состояние/продавец/локация/характеристики/фото/описание/
дата правки) — **гео-независимы** и парсятся как обычно, со строгой валидацией.

### 4.5. Фото и описание

- **Фото**: извлекаем только **список URL** (`image_urls`, размер `s-l1600`). Сами
  картинки **не качаем** — это забота оркестратора (S3 вне библиотеки).
- **Описание**: текст из ответа `itmdesc/{id}` (чистим теги). **Пустое** описание
  (ответ `200` с пустым телом) — валидно (`""`). Пример сырого описания —
  `examples/item_description_sample.html` (процедура — `examples/README.md`, раздел 2).
  А вот **HTTP-сбой** запроса описания (не-`200` / исчерпан ретрай) — **критичен** (по
  жёсткому, раздел 7.2): товар без описания не пишем. На практике `itmdesc`
  практически не падает.

### 4.6. Параллельность

Item-воркер тянет много товаров **параллельно** с **адаптивной конкуренцией**
(раздел 8). ebaydesc безлимитный (антибота нет), упираемся только в полосу сети.

## 5. Catalog-лейн

### 5.1. Открытая страница = живая сессия

Каталог-воркер получает **браузерную страницу** через колбэк `get_page` (браузер
поднимает оркестратор, в т.ч. с прокси). Страницу **прогреваем** на `www.ebay.com` —
она проходит антибот-challenge и становится **живой доверенной сессией**. Эта страница
**остаётся открытой** всё время работы воркера.

### 5.2. Запросы выдачи — in-page fetch с куками

Страницы выдачи (SRP) запрашиваем **`fetch`-ом изнутри открытой страницы** (через
исполнение JS в ней). То есть запрос делает **сам браузер** (его сетевой стек, его
TLS), а не внешний HTTP-клиент. Запросы:
- **same-origin** (страница на `www.ebay.com`, фетчим `www.ebay.com/sch/...`);
- **с куками сессии** (`credentials:'include'`) — несут антибот-клиренс и состояние
  сессии. Именно поэтому проходят без срабатывания антибота — это часть доверенной
  браузерной сессии.

Возвращается **сырой HTML выдачи без рендера** (быстро). `_stpos=19701` — в URL
(раздел 3.2), поэтому доставка в карточках корректна.

**Параллельность**: фетчим **батчами** (несколько SRP-запросов разом из одной
страницы), с **адаптивной конкуренцией** (раздел 8). Проверено: антибот на
параллельные in-page fetch не реагирует (раздел 13).

### 5.3. Классификация ответа, парсинг и пагинация

In-page fetch возвращает **полный серверный HTML** (без ленивого рендера), поэтому
**DOM-якорей не ждём**. Сначала **классифицируем** тело ответа существующим детектором
`page_state` (по `response.url` + `<title>`, не по DOM): Pardon / Access Denied — в
восстановление (раздел 7.3), Error Page — критично (раздел 7.2); иначе это SRP →
парсим.

Парсим **из DOM** (вёрстки карточек) — в выдаче цельной JSON-модели по карточкам нет
(в отличие от страницы товара). Переиспользуем существующий парсер выдачи (раздел 12):
из карточек берём `item_id`, заголовок, состояние, цену+валюту, **доставку**,
продавца, локацию, превью-фото. Пример распарсенных карточек — `catalog_dump.json`;
процедура получения — `examples/README.md` (раздел 3).

**Пагинация** (текущая логика): листаем с `_pgn=1`, `_ipg=240`; **стоп**, когда
страница вернула меньше 240 карточек (последняя) ИЛИ встретился сепаратор «Results
matching fewer words» ИЛИ достигнут кап страниц; **дедуп по `item_id`**; берём только
**точные** карточки (до сепаратора fewer-words).

### 5.4. Цена и доставка из каталога (в USD)

Карточки парсятся в **исходной валюте** листинга (§5.3 берёт сумму + сырой валютный
токен — карточки бывают не в USD: `'C $'`, `'EUR'`, `'£'`…). После сбора страниц
запроса **цена и платная доставка переводятся в USD** через fx-микросервис (один батч
на запрос; Free=0 и «не указана» не конвертируются). Доставка при этом **корректна к
нужному ZIP** (за счёт `_stpos=19701` в URL). Именно эти **USD-цена и USD-доставка**
используются как цена и доставка товара в Mode 1 (кто пишет — раздел 2.3).

### 5.5. Пустая выдача — это норма

У части артикулов выдача пустая (нет листингов). Это **легитимный результат** (пишем
каталог с 0 карточек, `task_done`), **не ошибка**.

## 6. Воркеры и контракты с оркестратором

### 6.1. Общие колбэки

- **`next_task`** — **одна** ручка получения задач (общая для обоих типов воркера).
  Возвращает **одну задачу за вызов** (`item_id` для item; артикул+фильтры+zip для
  каталога) или сигнал «задач нет». **Должна быть безопасна при параллельных вызовах**
  и отдавать **разные** задачи (очередь у оркестратора блокирует/помечает взятые).
- **`task_done`** — пометить задачу завершённой. Вызывается **строго после записи** в
  хранилище.
- **`store`** — клиент хранилища (раздел 12).

### 6.2. Item-воркер

`run_item_worker(next_task, task_done, store, *, <параметры конкуренции>)`

- **Браузер не нужен** (`get_page` не используется).
- Внутри — пул **N параллельных потребителей**: каждый в цикле «взять `next_task` →
  скачать товар (раздел 4) → записать → `task_done` → снова `next_task`». Поскольку
  потребителей N, в полёте всегда ~N товаров. `next_task` зовётся **параллельно**
  потребителями по мере завершения.
- **N (конкуренция) — адаптивная** (раздел 8), не хардкод.
- (Mode 2: добавятся параметры `item_cookie`, `item_proxy` — раздел 9.)

### 6.3. Catalog-воркер

`run_catalog_worker(get_page, next_task, task_done, store, *, zip="19701")`

- Держит **одну общую страницу** (`get_page` при старте, прогрев — раздел 5.1) на все
  потребители.
- Внутри — пул **N параллельных потребителей** (как у item, раздел 6.2): каждый берёт
  `next_task` (артикул) → in-page fetch его страниц выдачи → парс DOM → fx→USD →
  запись → `task_done`. В полёте всегда ~N запросов.
- **Конкуренция `C` — адаптивная** (раздел 8): общий лимит запросов в полёте по всем
  потребителям.
- **Координация общей страницы (мьютекс):** чинить страницу (swap при Access Denied /
  reload при Pardon, раздел 7.3) имеет право только **один** потребитель за раз —
  первый поймавший берёт мьютекс и выполняет починку, остальные ждут готовности и
  переотправляют свой запрос. Один swap/reload на всех, не N.

### 6.4. Жизненный цикл `get_page`

- `get_page` зовётся **при старте** каталог-воркера → получаем страницу.
- При **критической ошибке** (раздел 7) воркер **умирает** (исключение наружу).
  Восстановление — **забота внешнего оркестратора**: он решает, рестартить ли воркер;
  на рестарте `get_page` даёт **новую страницу с новым прокси**, что восстанавливает
  работу. Библиотека **сама не лечит** — просто падает.

## 7. Политика ошибок («по жёсткому»)

Базовый принцип: **структурные/критические ошибки → воркер умирает громко** (чтобы мы
сразу заметили и починили), **транзиент → ретрай**.

### 7.1. Транзиент (восстановимое)

Сетевой сбой / `503` / reset / timeout → **ретрай (до 3 раз)** с короткой паузой.
Если **ретраи исчерпаны** → это уже **критическая ошибка → воркер умирает** (см. 7.2).

### 7.2. Критические ошибки → смерть воркера

- **`ParseError`** — структура страницы/JSON-модели уехала или нет обязательного поля
  (раздел 7.4). Значит eBay сменил вёрстку/модель — падаем громко.
- **Транспортная смерть page** (net::ERR_*/краш/закрытие контекста) — инфраструктура
  браузера/прокси сломалась → **критически падаем** (оркестратор рестартит со свежим
  page+прокси, раздел 6.4).
- **Error Page** («SORRY — Something went wrong») → критически падаем.
- **ZIP-mismatch** (только Mode 2, раздел 9.3) → критически падаем.
- **Транзиент после исчерпания ретраев** (7.1) → критически падаем.

(**Access Denied** — НЕ здесь: это смерть **страницы**, а не воркера — лечится новой
страницей в сессии, см. 7.3.)

В **параллельном item-пуле**: одна критическая ошибка по любому товару → **падает
весь воркер** (все N задач в полёте без `task_done` → оркестратор их переотдаёт). Это
и есть «по жёсткому».

### 7.3. Восстановление страницы в сессии (каталог) — не фатал

Два события антибота на in-page fetch лечатся **в живой сессии** (воркер не умирает),
единым swap/reload на всех потребителей (механизм координации — раздел 6.3):

- **Pardon** («Pardon Our Interruption») → **reload** упавшего SRP-URL (реальная
  навигация исполняет challenge-JS и гасит его), запросы «в полёте» **бросаем** (им не
  доверяем) и переотправляем; адаптив режет `C ×backoff` (раздел 8). На проверенных
  темпах не срабатывает (раздел 13) — контур как **страховка**.
- **Access Denied** → «смерть **страницы**» (прокси/контекст флагнут антиботом):
  просим у воркера **новую страницу** (`get_page`), прогреваем, переотправляем
  запросы. Это **новый канал** → адаптив **сбрасывает `C` в низкий baseline** и
  разгоняется заново (раздел 8).

Прогресс артикула при обоих событиях сохраняется: уже распарсенные страницы пагинации
не теряем, переотправляем **только SRP-запрос(ы), что были в полёте**; `task_done`
не теряется.

### 7.4. Обязательные/опциональные поля (item)

- **Обязательные** (отсутствие → `ParseError` → смерть): `item_number`, `title`,
  `seller`, `location`, `specifics`.
- **Опциональные** (допустим `None`/пусто): `condition` (нет → «не указано»),
  `price_usd` и `shipping_cost` (в Mode 1 не парсятся вовсе — из каталога, раздел 4.4;
  заполняются только в Mode 2), `last_updated`.
- `image_urls` → пустой список, если у товара нет фото (это валидно, не ошибка).

## 8. Адаптивная конкуренция (в v1)

Конкуренцию (число параллельных запросов `C`) **не хардкодим** — её **подбирает сам
воркер**, нащупывая максимум, который тянет канал (прокси/браузер), без перегрузки.
Один и тот же алгоритм для обоих лейнов. **Верхнего потолка на `C` нет.**

### 8.1. Что меряем

Работаем **волнами/окнами**; после каждого окна меряем:
- **throughput** — запросов в секунду (выполнено / время окна);
- **реальную латентность** одного запроса (p50) — измеряется **внутри** запроса
  (время от старта до ответа), а не «время окна / C»;
- **ошибки/Pardon**.

### 8.2. Параметры (смысл каждого)

- **`C`** — сколько запросов держим «в полёте» одновременно. Это то, что подбираем.
  **Без потолка.**
- **окно** — сколько запросов меряем перед каждым решением (усреднение; чем больше
  окно, тем стабильнее замер и тише шум).
- **шаг роста** — на сколько увеличиваем `C` за успешное окно (напр. +25%,
  пропорционально: чем выше `C`, тем крупнее шаг).
- **baseline-латентность** — минимальная виденная латентность (низкий `C`, без
  очередей) = эталон «свободного» ответа.
- **`lat_rise`** — во сколько раз латентность должна превысить baseline, чтобы счесть
  «пошла очередь = насыщение» (напр. ×1.6).
- **`ε` (порог роста)** — насколько throughput должен вырасти, чтобы счесть «ещё
  растём» (напр. +5%), иначе — плато.
- **`backoff`** — во сколько режем `C` при ошибках/Pardon (напр. ×0.6).

### 8.3. Решение после окна

1. **Ошибки/Pardon** выше порога → `C × backoff` (режем); при Pardon — reload
   (раздел 7.3). Жёсткий сигнал перегрузки.
2. Иначе:
   - **throughput вырос (>ε)** и **латентность ровная (< lat_rise × baseline)** →
     `C += шаг` (есть запас, разгоняемся);
   - **throughput встал** ИЛИ **латентность полезла (≥ lat_rise × baseline)** →
     насытились → `C` чуть назад, держим (оседаем у «колена»).

Суть: лезем вверх, пока добавление `C` **реально ускоряет**; как только перестало
(упёрлись в полосу) или **латентность поползла** — фиксируемся. **Главный сигнал
предела — латентность** (на пределе рост `C` не даёт рост скорости, а лишь растит
очередь/латентность).

### 8.4. Статус и доводка (TODO)

Алгоритм **проверен живьём** (раздел 13): сам разгоняется до оптимума (для одного
браузера/прокси это оказалось ~`C≈100`, ~950 каталогов/мин, 0 антибота). **Логику
адаптива ещё дорабатываем** (раздел 11): окно усреднения (убрать осцилляцию),
адаптивный шаг (крупный на разгоне, мелкий у колена), мягче латентный backoff.

## 9. Mode 2 (реализуем позже)

Это **второй режим** item-лейна, **в v1 не реализуется**, но фиксируем дизайн.

Смысл: item-лейн становится **самодостаточным** — товар сам отдаёт **корректные цену
(нативный USD) и доставку** к нужному ZIP, не завися от каталога. Через US-egress eBay
печатает их сразу в USD (см. раздел 4.4 — там объяснено, почему в Mode 1 этого нет).

- **9.1. Прокси на item.** Запросы к ebaydesc идут **через US-прокси**. Доставка на
  ebaydesc считается по **гео IP запроса** (Akamai-edge), поэтому US-прокси даёт
  US-доставку.
- **9.2. Кука ZIP.** Чтобы доставка была к **точному** ZIP (19701, а не к дефолту
  гео прокси), в каждый запрос добавляем куку **`nonsession`** (она кодирует ZIP).
  **Минтим её один раз** (визит страницы выдачи с `_stpos=19701` через браузер/
  curl_cffi → достаём `nonsession`) и **хардкодим/передаём** в item-лейн. Кука
  **прокси-независима**. (Срок жизни куки — TODO, раздел 11.)
- **9.3. ZIP-check.** На каждом ответе **проверяем `shipToLocation == 19701`**; не
  совпало (кука протухла / прокси не US / гео уехало) → **критическая смерть**
  (раздел 7.2) — чтобы никогда не записать молча неверную доставку.
- **9.4. Цена и доставка из item.** Тогда **цену (нативный USD) и доставку** парсим из
  товара, а не из каталога. Поля `price_usd`/`shipping_cost` модели товара
  заполняются (в Mode 1 они `None` — раздел 7.4). Проверка цены-в-USD — TODO (раздел
  11).
- **9.5. Масштаб.** Единица масштаба — **прокси**: **один воркер на прокси**, каждый
  с адаптивной конкуренцией (раздел 8). Масштаб = число прокси.

Требование консистентности (TODO, раздел 11): доставка в карточке каталога (SRP)
должна совпадать с доставкой на странице товара (PDP) — иначе Mode 1 и Mode 2 дадут
разную доставку.
