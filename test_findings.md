## Часть 1. ОШИБКИ (симптом → корень → статус)

### 1. [Item, этап 1] выбор модели «по размеру» → бралась реклама — ✅ ИСПРАВЛЕНО (предв.)
- **Симптом:** `ParseError item_number` (и др. поля) на части товаров. Сначала списывал
  на `impersonate`, причина глубже.
- **Корень:** на странице несколько объектов `"modules":{...}`; старый `_largest_modules`
  брал **самый длинный**. Рекламные `MERCH_PLACEMENT_*` бывают **крупные** (живьём — до
  **136 КБ, 1 раздел**) и на impersonate-версии иногда **обгоняли** настоящую модель
  (56–60 разделов) → выбор брал рекламу → нет полей → `ParseError`.
- **Частота:** интермиттентная (1/59 и 0/300 в прогонах) — зависит от товара/момента.
- **Фикс:** `_main_modules` — выбор по **числу якорных разделов** (`ITEM_SPEC_SUMMARY`/
  `JSONLD`/`TITLE`/`PICTURE`/`BUY_BOX` — есть только в модели, у рекламы 0), не по
  размеру. Живьём **659/659 = 100%** на обеих версиях. ⚠️ предв.: завязано на ИМЕНА
  разделов; used/вариативные не проверены.
- **Статус:** применён в `ebay_library/html/item.py`; юнит-тесты зелёные (8+4+6).

### 2. [Catalog, этап 7] `ParseError 'seller'` — продавцы без рейтинга — 🔧 ОТКРЫТО
- **Сообщение:** `ParseError field 'seller' failed (id=…, raw=None)` — ~11 карточек.
- **Корень:** `srp.py` `_SELLER_RE = "^<ник>\\s+NN% positive"` — у новых/0-feedback
  продавцов eBay не печатает «% positive» → seller=None → `ParseError` (seller обязателен).
- **Влияние:** критично (валит задачу/воркер).
- **Фикс (направление):** добыть живой HTML такой карточки → расширить извлечение ника
  (без «% positive») ЛИБО сделать seller опциональным для каталог-карточки.

### 3. [Catalog, этап 7] `ParseError 'price'` — «See price» — 🔧 ОТКРЫТО
- **Сообщение:** `ParseError field 'price' failed (id=358634704324, raw='See price')`.
- **Корень:** карточка показывает текст **«See price»** (MAP-цена), а не число; регекс
  цены этого не ждёт. price обязателен. Редко (1/18672 карточек, 1/150 задач).
- **Фикс (направление):** трактовать «See price» (price опционально для таких карточек,
  или отбрасывать карточку) — после просмотра живой разметки.

### 4. [fx, этап 5] fd-exhaustion под конкуренцией — 🔧 ОТКРЫТО
- **Сообщения:** `OSError [Errno 24] Too many open files` ×3, `ConnectError` ×15,
  `RemoteProtocolError` ×1 (≈19/150 задач).
- **Корень:** `http/fx.py` `convert_cards` создаёт `httpx.AsyncClient` **на каждый
  вызов** с `limits(max_connections=None)` → при 12 параллельных задачах лавина соединений
  к fx-сервису → исчерпание дескрипторов.
- **Влияние:** критично для каталог-воркера (этап 9) под нагрузкой.
- **Фикс (направление):** один общий httpx-клиент с лимитом коннектов (пул), один на
  воркер, не на вызов. Возможно поднять `ulimit -n` как подпорку.

### 5. [Stage 8] обрыв fetch при навигации = «Failed to fetch» — 🧪 ИСПРАВЛЕНО офлайн (артефакт)
- **Находка:** обрыв in-flight fetch при нашей навигации даёт `TypeError: Failed to
  fetch` (а не документированное «Execution context was destroyed»), и это **дословно
  то же**, что реальный сетевой сбой → по тексту не различить.
- **Фикс дизайна:** **event+epoch** (счётчик починок различает «оборвала починка» vs
  «настоящий сбой») + **ready-ворота** (новые fetch не стартуют во время починки). Офлайн
  16/16; обрыв подтверждён живьём (10/10). **В проект не записано.**

### 6. [Stage 8] goto на упавший SRP-URL ломает следующий fetch — 🧪 ИСПРАВЛЕНО (артефакт)
- **Находка:** после `goto(SRP-URL)` следующий fetch падает ~17% (5/6); после
  `goto(главная)` — 6/6 ok (чистая изоляция на здоровом прокси).
- **Фикс:** reload делать через **главную** (= повторный `warmup`), не через упавший URL.
  Подтверждено живьём. **В проект не записано.**

### 7. [Stage 2, разрешено] `ParseError item_number` от impersonate
- Симптом ошибки #1; «фикс» — убрать `impersonate` (ebaydesc, en-US). Уже сделано в
  `http/fetch.py`. Открытого бага нет (корневая причина — #1).

## Часть 2. РЕШЕНИЯ / обсуждённое

- **Контур-8: event+epoch + ready-ворота** (а не классификация ошибки по тексту) — текст
  обрыва неинформативен.
- **Reload → главная** (`warmup`), не упавший URL — живой тест.
- **`warmup` остаётся примитивом** (двойная роль: первичный прогрев + снятие Pardon).
  **`_reload` → `_recover_pardon`** (честное имя; применить при записи контура в проект).
- **Контур восстановления живьём не вызвать** (0 антибота даже при conc=64) → **держим
  как страховку, не упрощаем** до «умри-рестартни»; реальные антиботы ловим в проде.
- **Без лимита починок** (re-warm/swap до победного; контроллер тормозит).
- **goto Timeout → критически падаем** (уже так; §7.2).
- **impersonate не используем** (ebaydesc без WAF; impersonate отдаёт другую страницу).
- **Полная валидация контура-8** (Pardon→reload end-to-end) — только **инжектом**
  (форс синтетического Pardon на живой вкладке), т.к. естественно не вызывается. Отложено.
